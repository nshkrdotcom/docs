Reading through all six files, the design is remarkably thorough. The missing pieces I'd flag fall into a few categories:

**The human process side is almost entirely absent.** The system models artifacts, evidence, commitments, and lineage, but it doesn't model *who decides what counts as architecture*. There's no concept of architectural governance process: how a proposed commitment gets reviewed, who has standing to accept it, how disagreements between architects get resolved, what happens when the business overrides the technical decision. The `approval_required` fields gesture at this but don't model the process itself.

**The system assumes architecture exists to be discovered.** Most of the design treats architecture as something latent in the codebase waiting to be extracted. But in practice, a significant portion of architectural decisions were never written down anywhere — they live in people's heads, emerged from undocumented conversations, or were implicit in the original team's shared understanding. There's no first-class concept of *known unknowns* at the architectural level: commitments that someone knows should exist but haven't been formalized yet.

**Change propagation across organizational time is missing.** The lineage model handles technical change across commits and snapshots. But it doesn't model organizational change: team reorganizations, engineer departures, acquired codebases, ownership handoffs. The system would struggle to answer "this module was built by a team that no longer exists and no current engineer understands its original intent."

**The commitment DSL has no composability or inheritance.** Commitments are currently flat. Real architecture has layered rules: platform-wide rules, domain-specific overrides, app-specific exceptions, and temporary derogations from any of those. Without a way to say "this commitment inherits from the platform policy but relaxes X for this bounded context," the DSL becomes unwieldy at scale.

**Conflict between dimensions isn't modeled.** The system can assign an artifact coordinates across many dimensions, but what happens when those dimensions pull in opposite directions? A function might be high-risk (should be changed cautiously) but also on a hot path (needs to change urgently). The system needs a framework for resolving competing pressures, not just a way to express them separately.

**The "diagonal" navigation is underspecified operationally.** The design repeatedly promises diagonal navigation — jumping from a function to a risk cluster to a cross-cutting concern — but the materialization strategy for this is thin. The star-from-defaults coverage policy for projection states doesn't address how diagonal paths are precomputed. Navigation along dimensions that don't follow the structural or causal graph is the hardest part to make fast, and the design mostly defers it.

**There's no model for external interface evolution.** The system models internal architecture deeply but treats external systems (Stripe, email providers, databases) as leaf nodes. For serious systems, the *evolution of external interfaces* — API version changes, deprecation timelines, provider migration — is itself an architectural concern that generates requirements, commitments, and drift. The current design can't reason about "we're on Stripe API v2 and v3 is breaking, what does that touch?"

**The inference pipeline has no prioritization model.** The system knows what to analyze but not what to analyze *first*. For a large workspace, you can't annotate everything at once. There's no concept of salience-driven analysis scheduling: which functions most need LLM analysis, which commitments most need verification, which drift findings most need runtime evidence. Without this, the system either under-covers important areas or burns resources on low-value annotations.

The biggest single gap: the design models software as a *product* to be understood, but barely models software development as a *practice* to be supported. The human workflow — how a team actually moves from vague requirement to deployed feature while maintaining architectural coherence — is described only in terms of artifacts the team produces, not the collaborative, iterative, often messy process by which those artifacts come to exist and get trusted.
