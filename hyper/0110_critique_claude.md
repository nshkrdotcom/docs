Reading all three documents together, the remaining gaps cluster around a few themes that still haven't been addressed.

**The system has no model of its own knowledge boundary.** It knows what it has indexed, what it has analyzed, and what evidence exists. But it doesn't have a principled model of what it *cannot* know by design: dynamic dispatch that can never be statically resolved, runtime behavior that only manifests under specific load conditions, configuration that lives outside the repository, architecture decisions made verbally and never recorded, provider behavior that isn't documented anywhere. These aren't just unknowns to be elicited — they're permanent epistemic limits. The system needs to distinguish "we haven't analyzed this yet" from "this class of fact is not discoverable through any analysis we could run." Without that distinction, users will keep searching for evidence that doesn't exist, and the system will keep appearing to promise answers it structurally cannot give.

**Learning is modeled as updating priors, but the system has no theory of concept drift.** The architecture of a system genuinely changes over time — not just through specific decisions, but through gradual evolution of what terms mean, what boundaries feel natural, which patterns the team considers normal. A bounded context that was clear two years ago may have become genuinely ambiguous as the codebase grew. The system's learning model assumes concepts are stable and corrections refine the model toward a fixed truth. But sometimes the truth itself has moved. There's no model for detecting that the system's mental model of the codebase has drifted from the codebase's actual conceptual structure, or for triggering reconceptualization rather than incremental correction.

**The architecture of the system's own outputs is unmodeled.** The system produces many things: PR comments, CI checks, ADR drafts, generated tests, projection packets, query answers, debt items, remediation plans. These outputs have their own architecture: they reference each other, they become stale, they conflict, they accumulate. There's no model for the output artifact graph — which generated test was produced in response to which finding, which ADR draft superseded which earlier draft, which debt item is the upstream cause of which open loop. Without this, the system's outputs become their own form of entropy. An engineer six months later finds three generated tests, two ADR draft fragments, an expired exception, and an unresolved open loop, with no way to understand how they relate or which are still relevant.

**The transition between tools is unmodeled.** Teams use many tools: issue trackers, wikis, Slack, design tools, calendar, code review platforms. The system has a strong internal model but no theory of how it relates to the tool ecosystem around it. This matters because architecture decisions actually happen *in* those other tools — in Slack threads, Jira tickets, Notion pages, Figma comments. The system can ingest some of this as source documents, but it doesn't model the workflow integration: how a governance verdict becomes a Jira ticket, how a known unknown becomes a Linear issue, how a PR finding becomes a Slack notification that gets the right response, how a debt item gets attached to a quarterly planning cycle. The result is that the system produces high-quality architecture intelligence that exists in a silo, requiring manual translation into the tools where engineering work actually gets coordinated.

**There's no model of attention economics at the team level.** The inference scheduler handles computational priority, but there's a separate scarcer resource: team attention. A team can process roughly N architecture findings per sprint before finding fatigue sets in and they start ignoring everything. The system has no model for this. It can produce a high-fidelity picture of fifty architecture problems, but with no theory of how many findings a team can usefully absorb, no model of finding fatigue, no concept of a "finding budget" per team or per PR, and no ability to curate rather than enumerate. The result is the classic problem of security tools and linters: once noise exceeds a threshold, everything gets ignored including the important things.

**The identity of "architecture" is itself unmodeled.** The entire design assumes architecture is a thing that exists and can be represented. But in practice, the architecture of a system is partly a social construction: different people on the same team would draw the bounded contexts differently, have different opinions about what counts as a boundary violation, disagree about whether this function belongs in Billing or Shared Kernel. The system has human correction and governance, but it doesn't model the underlying fact that there can be multiple valid architectures for the same codebase, that architectural views are perspectival, and that the "correct" architecture is sometimes genuinely underdetermined rather than merely unknown. A strong governance model will resolve some of these disputes, but others reflect genuine legitimate disagreement that shouldn't be collapsed into a single authoritative answer. The system needs a concept of architectural pluralism — multiple coexisting views that are valid from different perspectives — rather than treating every disagreement as a temporary state on the way to a single correct answer.

The thread connecting most of these is that the design is built around a correspondence theory of architecture: there is a real architecture, the system tries to discover it, and correctness means matching reality. But architecture is partly constitutive — it's partly defined by the representations the team agrees to use, the conversations they have, the models they maintain. The system is excellent at the correspondence side but hasn't fully reckoned with the constitutive side, where the tool doesn't just describe architecture but participates in making it.
