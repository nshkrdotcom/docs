# Response 1 — Belief Calculus for the Operating Intelligence Kernel

The existing design already has a strong representational substrate: AST-anchored entities, dimensional understanding slices, semantic clusters, materialized projections, and navigation indices designed so the UI reads precomputed state rather than doing inference live. 

The missing layer is the thing that decides:

```text
What does the system currently believe?
Why?
With what confidence?
Under what scope?
What changed?
What became stale?
What is contradicted?
What needs action?
```

This first gap-filling response defines that layer: the **Belief Calculus**.

---

# 1. Core Claim

A software intelligence system should not store “facts.”

It should store and continuously revise **claims**.

A claim is a proposition about the software system, such as:

```text
Password reset tokens expire after 15 minutes.

Billing must not directly read Accounts-owned tables.

Accounts.reset_password/2 implements the password reset confirmation flow.

The Reporting app violates the Billing data ownership boundary.

This runtime path is rare.

This function exists to preserve non-enumeration behavior.

This test verifies expired reset token rejection.
```

Each claim has:

```text
supporting evidence
contradicting evidence
scope
freshness
authority
confidence
current belief state
```

The engine’s job is to compute the current belief state from available evidence.

---

# 2. Why Confidence Scores Alone Are Insufficient

A simple `confidence: 0.82` is not enough.

Two claims can both have 0.82 confidence but mean very different things:

```text
Claim A:
  Strongly supported by code, tests, and human confirmation.

Claim B:
  Generated by an LLM from naming conventions with no direct evidence.

Claim C:
  Supported by old docs but contradicted by current runtime traces.

Claim D:
  True in prod but false in test.

Claim E:
  Intended by architecture but not implemented in code.
```

All of those need different behavior.

So the system needs a richer computed belief record:

```json
{
  "belief_state": "drifted",
  "support_score": 0.78,
  "refute_score": 0.64,
  "confidence": 0.71,
  "freshness": 0.92,
  "contestation": 0.64,
  "authority_basis": ["accepted_requirement", "current_code"],
  "scope": {
    "snapshot": "prod-2026-05-17",
    "environment": "prod",
    "apps": ["accounts"]
  },
  "recommended_action": "require_architecture_update_or_code_revert"
}
```

The belief state is the product. The score is only one input.

# 3. Claim Types

The belief engine needs to know what kind of claim it is evaluating, because different evidence matters for different claim types.

## Primary claim classes

| Claim Type                  | Example                                            | Strongest Evidence                                     |
| --------------------------- | -------------------------------------------------- | ------------------------------------------------------ |
| **Intent claim**            | “This feature exists to support account recovery.” | requirements, ADRs, user annotation, code rationale    |
| **Architecture commitment** | “Billing must not read Accounts tables.”           | accepted architecture policy, ADR, human architect     |
| **Implementation claim**    | “This function verifies token expiry.”             | current code, AST/static analysis, tests               |
| **Verification claim**      | “This behavior is tested.”                         | test code, test execution results                      |
| **Runtime claim**           | “This path is hot in production.”                  | telemetry, traces, metrics                             |
| **Ownership claim**         | “This module belongs to Shared Kernel.”            | CODEOWNERS, human correction, repo conventions         |
| **Contract claim**          | “This API accepts this payload shape.”             | specs, tests, observed traffic, docs                   |
| **Causal claim**            | “Changing this requirement affects this function.” | trace paths, dependency paths, implementation bindings |
| **Policy claim**            | “This PR violates an architecture rule.”           | policy DSL, source evidence, graph edge                |
| **Historical claim**        | “This decision superseded the old design.”         | lineage, ADR history, commits                          |

The same evidence can mean different things depending on claim type.

For example, current code can strongly prove:

```text
This implementation currently uses max_age: 3600.
```

But current code does **not** prove:

```text
The intended architecture is to use a 60-minute reset token.
```

That distinction matters.

---

# 4. Evidence Types and Authority

Evidence is not uniform. A runtime trace, an ADR, a test, a code span, and an LLM summary are different kinds of signal.

## Evidence classes

| Evidence Type           | What It Is Best At Proving                       | What It Cannot Safely Prove                        |
| ----------------------- | ------------------------------------------------ | -------------------------------------------------- |
| **Current source code** | Actual implementation structure                  | Intended architecture                              |
| **AST/static analysis** | Calls, dependencies, syntax-level behavior       | Runtime frequency or dynamic dispatch certainty    |
| **Tests**               | Verified expected behavior under test conditions | Production behavior                                |
| **Passing CI**          | Current test suite did not catch an issue        | That behavior is correct                           |
| **Runtime traces**      | Observed production behavior                     | Full possible behavior                             |
| **Telemetry metrics**   | Frequency, latency, errors, hotness              | Original design intent                             |
| **Requirements docs**   | Desired behavior                                 | Current implementation                             |
| **ADRs**                | Accepted design decisions                        | Current compliance                                 |
| **Human correction**    | Local domain truth or policy intent              | Automatically all similar cases                    |
| **LLM inference**       | Hypotheses, summaries, likely mappings           | High-authority truth without evidence              |
| **Absence of evidence** | Possible missing implementation/test             | Definitive nonexistence, unless search is complete |

The calculus should use **contextual authority**, not one global ranking.

---

# 5. Contextual Authority Matrix

The system should evaluate evidence differently depending on what is being claimed.

| Claim Being Evaluated              | Highest-Authority Evidence                   | Medium Evidence            | Weak Evidence       |
| ---------------------------------- | -------------------------------------------- | -------------------------- | ------------------- |
| “What does the code currently do?” | current code, AST, tests                     | runtime traces             | docs, LLM           |
| “What was intended?”               | accepted requirements, ADRs, human architect | design docs, issue history | current code, LLM   |
| “What happens in production?”      | runtime traces, metrics, logs                | code, tests                | docs                |
| “What is verified?”                | test assertions, contract tests, CI result   | runtime observations       | code comments       |
| “What is architecturally allowed?” | commitment DSL, ADR, policy, human override  | inferred boundaries        | call graph alone    |
| “Who owns this?”                   | CODEOWNERS, explicit annotation              | repo/team conventions      | namespace guess     |
| “What should change if X changes?” | derivation edges, contracts, policies        | call/dependency graph      | semantic similarity |

This prevents bad conclusions like:

```text
The code does X, therefore X must be the intended architecture.
```

or:

```text
The ADR says X, therefore the code still implements X.
```

The system should instead say:

```text
The intended architecture says X.
The current implementation says Y.
Therefore this is architecture drift.
```

# 6. Evidence Scoring

Each evidence item should be converted into a normalized signal for a claim:

```text
support
refute
neutral
```

For a given claim `C` and evidence item `E`, compute:

```text
support_strength(E, C)
refute_strength(E, C)
relevance(E, C)
authority(E, C)
freshness(E)
specificity(E, C)
directness(E, C)
independence(E)
calibration(E.source)
```

Then compute an effective evidence weight:

```text
effective_weight =
  authority
  × relevance
  × freshness
  × specificity
  × directness
  × independence
  × calibration
```

## Dimensions of evidence quality

| Dimension      | Meaning                                                    |
| -------------- | ---------------------------------------------------------- |
| `authority`    | How trusted this evidence type is for this claim type      |
| `relevance`    | Whether it actually addresses the claim                    |
| `freshness`    | Whether it is still valid after code/doc/runtime changes   |
| `specificity`  | Whether it refers to the exact artifact or a broad area    |
| `directness`   | Whether it directly proves the claim or only implies it    |
| `independence` | Whether it is independent or redundant with other evidence |
| `calibration`  | Historical reliability of the analyzer, model, or source   |

Example:

```text
Claim:
  Password reset token expiry is 15 minutes.

Evidence A:
  Code span has max_age: 900.
  authority: high for implementation claim
  specificity: exact
  directness: high
  freshness: high
  support: strong

Evidence B:
  Old ADR says 15 minutes.
  authority: high for intent claim
  specificity: high
  directness: high
  freshness: medium if ADR not updated recently
  support: strong for intent, medium for implementation

Evidence C:
  LLM summary says “short-lived token.”
  authority: low
  specificity: medium
  directness: low
  support: weak
```

# 7. Combining Evidence

The belief engine should not simply average evidence.

Averaging causes bad behavior. One weak contradicting signal can water down five strong signals, and many duplicate weak signals can overwhelm one strong signal.

A better approach is to maintain separate support and refutation channels.

For a claim `C`:

```text
support_score = combined strength of supporting evidence
refute_score  = combined strength of contradicting evidence
freshness     = freshness of the evidence basis
contestation  = min(support_score, refute_score)
belief_margin = support_score - refute_score
```

A simple combining function:

```text
combined_support = 1 - Π(1 - weighted_support_i)

combined_refute = 1 - Π(1 - weighted_refute_i)
```

This allows multiple independent evidence items to increase confidence while preventing unlimited inflation.

Then:

```text
belief_margin = combined_support - combined_refute
contestation = min(combined_support, combined_refute)
```

High support and low refutation:

```text
verified / believed
```

Low support and high refutation:

```text
refuted
```

High support and high refutation:

```text
contested / drifted / scope conflict
```

Low support and low refutation:

```text
unknown / underspecified
```

# 8. Belief States

The system should compute discrete states from the evidence profile.

## Core belief states

| State           | Meaning                                                        |
| --------------- | -------------------------------------------------------------- |
| `unknown`       | Not enough evidence either way                                 |
| `inferred`      | Plausible but weakly supported                                 |
| `believed`      | Supported by good evidence, low contradiction                  |
| `verified`      | Strong direct evidence, usually code + test, human, or runtime |
| `contested`     | Strong support and strong contradiction                        |
| `refuted`       | Strong contradiction, weak support                             |
| `stale`         | Evidence was once valid but source changed                     |
| `drifted`       | Intended architecture and actual implementation diverge        |
| `orphaned`      | Artifact remains but upstream rationale disappeared            |
| `unimplemented` | Requirement or commitment lacks downstream realization         |
| `unverified`    | Implementation exists but no verification evidence             |
| `superseded`    | Replaced by a newer claim                                      |
| `scope_split`   | True in one scope but false in another                         |
| `exceptioned`   | Violates general rule but has explicit accepted exception      |

The key states for novelty are:

```text
drifted
unimplemented
orphaned
unverified
scope_split
exceptioned
```

Those are product states, not just database labels.

---

# 9. State Classification Rules

The exact thresholds should be calibrated over time, but the first version can use explicit decision rules.

Example rule set:

```text
verified:
  support_score >= 0.85
  refute_score < 0.20
  at least one high-authority direct evidence item

believed:
  support_score >= 0.65
  refute_score < 0.35

inferred:
  support_score >= 0.40
  refute_score < 0.35
  no high-authority direct evidence

contested:
  support_score >= 0.50
  refute_score >= 0.50

refuted:
  refute_score >= 0.75
  support_score < 0.40

stale:
  source hash or dependency hash changed
  and no recomputed evidence exists

unimplemented:
  upstream requirement/commitment is accepted
  and no implementation binding is found
  after complete-enough search

unverified:
  implementation binding exists
  and verification binding is absent or stale

drifted:
  accepted intent/commitment conflicts with current implementation or runtime evidence

scope_split:
  conflicting evidence is valid in different scopes

exceptioned:
  violation exists
  but accepted exception evidence applies
```

The important point: **state is computed from evidence and scope**, not manually assigned.

# 10. Contradiction Taxonomy

Not all contradictions are the same.

The system should classify contradiction type before deciding what to do.

## Common contradiction types

| Contradiction             | Example                                      | Likely Interpretation                   |
| ------------------------- | -------------------------------------------- | --------------------------------------- |
| `doc_code_drift`          | ADR says 15 min, code says 60 min            | Architecture drift                      |
| `requirement_test_gap`    | Requirement exists, no tests                 | Unverified implementation               |
| `test_code_mismatch`      | Test expects old behavior, code changed      | Failing/stale test or unintended change |
| `runtime_design_mismatch` | Design says rare path, runtime says hot      | Risk model update                       |
| `policy_exception`        | Boundary violation with approved exception   | Exceptioned violation                   |
| `scope_conflict`          | True in test, false in prod                  | Scope split                             |
| `stale_requirement`       | Code removed, requirement still active       | Unimplemented or obsolete requirement   |
| `human_model_conflict`    | Human says Shared Kernel, model says Billing | Human correction becomes prior          |
| `static_runtime_conflict` | Static path possible, runtime never observed | Possible cold path or dead code         |
| `ownership_conflict`      | CODEOWNERS and inferred ownership differ     | Ownership ambiguity                     |

The system should not flatten all of these into:

```text
contradiction: true
```

It should produce typed operational states.

---

# 11. Scope Is Mandatory

Many “contradictions” disappear when scoped correctly.

A claim may be true in:

```text
dev
test
staging
prod
one repo snapshot
one release
one branch
one tenant
one feature flag state
one OTP app
one runtime service
```

Example:

```text
Claim:
  Billing sends invoice events asynchronously.

Evidence:
  In prod, events are sent through Oban.
  In test, code uses inline adapter.
```

This should not be marked as a contradiction.

It should become:

```text
scope_split:
  prod: verified async
  test: verified inline
```

So every belief should carry scope:

```json
{
  "environment": "prod",
  "snapshot": "release-2026.05.17",
  "runtime_service": "billing-api",
  "feature_flags": {
    "new_invoice_pipeline": true
  }
}
```

A belief without scope is almost always dangerous.

# 12. Freshness and Invalidation

A claim can be well-supported and still stale.

Freshness should be computed from dependency hashes.

Every claim should know what it depends on:

```text
source spans
AST nodes
test files
runtime observation windows
documents
requirements
ADRs
policies
human annotations
dependency graph edges
config keys
```

When any dependency changes, the claim becomes either:

```text
still valid
needs recomputation
stale
partially stale
```

## Freshness categories

| Freshness State      | Meaning                                      |
| -------------------- | -------------------------------------------- |
| `fresh`              | Evidence matches current artifact hashes     |
| `locally_stale`      | Direct source changed                        |
| `upstream_stale`     | Requirement/decision/policy changed          |
| `downstream_stale`   | Implementation/test/runtime evidence changed |
| `scope_stale`        | Environment/snapshot changed                 |
| `historically_valid` | Was true in prior snapshot                   |
| `revalidated`        | Rechecked after change                       |

Example:

```text
Claim:
  Accounts.reset_password/2 verifies token expiration.

Dependency:
  source span of Accounts.Token.verify/1

Code changes:
  verify/1 no longer passes max_age.

Result:
  implementation claim becomes stale immediately.
  after static reanalysis, it becomes refuted.
  upstream requirement becomes drifted.
  tests become must_revalidate.
```

---

# 13. Belief Propagation

Claims are connected. Belief changes should propagate through derivation edges.

Example chain:

```text
Requirement
  → Architecture commitment
    → Contract
      → Implementation
        → Test
          → Runtime observation
```

## Propagation principles

### Downstream propagation

If an upstream claim changes:

```text
requirement changed
ADR superseded
policy changed
contract changed
```

then downstream claims may become:

```text
must_revalidate
possibly_stale
no_longer_sufficient
incorrect_under_new_requirement
```

### Upstream propagation

If downstream evidence changes:

```text
code changed
test removed
runtime behavior changed
```

then upstream claims may become:

```text
unimplemented
unverified
drifted
partially_implemented
```

### Lateral propagation

If related artifacts share a commitment:

```text
several modules implement same API contract
several apps follow same boundary rule
several tests verify same invariant
```

then a correction or contradiction in one area may affect sibling claims.

---

# 14. Propagation by Edge Type

Different trace edges propagate differently.

| Edge Type       | Propagation Meaning                                                    |
| --------------- | ---------------------------------------------------------------------- |
| `extracts`      | If source doc changes, extracted requirement may be stale              |
| `refines`       | If parent requirement changes, child requirement may need revalidation |
| `motivates`     | If motivating requirement is removed, decision may become orphaned     |
| `constrains`    | If constraint changes, implementation must be checked                  |
| `implements`    | Implementation evidence can support or refute requirement realization  |
| `verifies`      | Test evidence supports verification, not necessarily full correctness  |
| `observes`      | Runtime evidence confirms occurrence or frequency                      |
| `supersedes`    | Older claim becomes superseded unless still active in another scope    |
| `violates`      | Policy violation changes state of both edge and commitment             |
| `exception_for` | Accepted exception changes violation behavior                          |
| `depends_on`    | Upstream change may trigger causal impact analysis                     |
| `owns`          | Ownership corrections update future inference priors                   |

The propagation rule must be tied to edge semantics.

A generic graph traversal is not enough.

# 15. The Belief Revision Loop

On every meaningful event, the system should run a local belief revision cycle.

## Events

```text
code file changed
test added
test removed
test result changed
doc changed
ADR changed
requirement changed
runtime trace ingested
policy changed
human correction added
dependency changed
PR opened
release snapshot created
```

## Revision process

```text
1. Identify directly affected artifacts.
2. Mark dependent evidence as stale.
3. Re-run relevant extractors/analyzers.
4. Recompute evidence weights.
5. Recompute claim support/refute scores.
6. Classify belief states.
7. Detect contradictions and drift.
8. Propagate effects upstream/downstream.
9. Update materialized projections.
10. Produce user-facing deltas and actions.
```

Pseudo-code:

```text
on_event(event):
  affected = find_affected_artifacts(event)

  stale_claims = invalidate_claims_depending_on(affected)

  new_evidence = run_relevant_analyzers(affected)

  candidate_claims =
    stale_claims
    ∪ claims_supported_by(new_evidence)
    ∪ claims_refuted_by(new_evidence)
    ∪ upstream_claims(candidate_claims)
    ∪ downstream_claims(candidate_claims)

  for claim in candidate_claims:
    evidence = collect_evidence(claim)
    belief = evaluate_belief(claim, evidence)
    persist_belief_state(claim, belief)

  contradictions = detect_contradictions(candidate_claims)
  impacts = propagate_belief_changes(candidate_claims, contradictions)

  update_projection_packets(impacts)
  emit_action_recommendations(impacts)
```

The important property is locality.

The system should not recompute the whole universe after every change.

# 16. Belief Explanation

Every belief state should be explainable.

A belief explanation should answer:

```text
What does the system believe?
What supports it?
What contradicts it?
What changed recently?
What is the scope?
What is uncertain?
What action should be taken?
```

Example:

```text
Belief:
  Password reset token expiry is drifted.

Current state:
  Intended policy: 15 minutes.
  Current implementation: 60 minutes.

Supporting intent evidence:
  SEC-014 says reset tokens expire after 15 minutes.
  ADR-008 selected 15-minute expiry after security review.

Contradicting implementation evidence:
  Accounts.Token.verify_reset_token/1 now passes max_age: 3600.

Verification impact:
  Existing expiry test expects 900 seconds and is now stale or failing.

Recommended action:
  Restore max_age: 900, or update SEC-014, ADR-008, tests, and user-facing docs.
```

This explanation is much more valuable than:

```text
confidence: 0.61
```

# 17. Absence Evidence

Absence matters, but it is dangerous.

The system should distinguish:

```text
No evidence found
```

from:

```text
Evidence cannot exist
```

from:

```text
Search was complete enough that absence is meaningful
```

Example:

```text
Requirement:
  Password reset expiration must be tested.

Search result:
  No test found.

But:
  test indexing only covered 40% of repo.

State:
  unknown / insufficient search

If:
  test indexing covered all test files
  no relevant assertion found
  no runtime contract test found

State:
  unverified
```

Absence evidence needs a **search completeness score**.

```json
{
  "absence_evidence": true,
  "search_scope": "all indexed ExUnit tests",
  "search_completeness": 0.94,
  "missing_artifact_kind": "verification",
  "belief_effect": "supports_unverified_state"
}
```

This avoids false claims like:

```text
This is untested.
```

when the system simply failed to search enough.

# 18. Runtime Evidence

Runtime evidence needs special handling.

Runtime traces are powerful but incomplete. They prove observed behavior, not all possible behavior.

## Runtime can prove

```text
this path occurred
this path is hot
this service called that service
this latency distribution exists
this error happened
this feature flag was active
this event was emitted
```

## Runtime cannot prove by itself

```text
this path is impossible
this behavior is intended
this architecture is correct
this code is fully tested
```

Runtime evidence should update:

```text
hotness
risk
drift
coverage priority
performance assumptions
operational reality
```

Example:

```text
Design claim:
  Password reset request is low-frequency.

Runtime evidence:
  40% of auth-related traffic is password reset due to bot abuse.

Belief update:
  original frequency assumption refuted
  abuse-case requirement should be promoted
  rate limiting commitment becomes high priority
  tests and telemetry projections gain salience
```

Runtime-to-intent feedback is one of the strongest novelty areas.

---

# 19. Human Corrections as High-Authority but Scoped Evidence

Human annotations should not blindly override everything globally.

They should become high-authority evidence within a scope.

Example correction:

```text
This module belongs to Shared Kernel, not Billing.
```

The belief engine should update:

```text
module ownership: verified by human
bounded context membership: corrected
similar modules: prior adjusted, not automatically relabeled
boundary violations: recomputed
projection salience: updated
future clustering: retrained or reweighted
```

Human correction should produce:

```text
direct belief update
local propagation
future inference prior
calibration feedback
```

But it should preserve scope:

```text
Who said it?
What authority level?
Does it apply to this module only?
This namespace?
This repo?
This snapshot?
Future snapshots?
```

A senior architect’s correction may become a durable workspace prior.

A one-off developer note may apply only to a specific artifact.

# 20. Confidence Calibration

The system should not trust raw LLM confidence.

Every analyzer should develop a reliability profile.

## Calibration dimensions

```text
analyzer type
model version
prompt template
claim type
evidence type
artifact type
language feature
repo/project
human correction history
```

Example:

```text
LLM summaries of function intent:
  historically 82% correct after human review.

LLM bounded context clustering:
  historically 64% correct.

Static call extraction:
  96% correct for normal calls.
  55% correct for dynamic apply/macro-generated calls.

Runtime trace edge:
  99% correct for observed calls.
  incomplete for unobserved calls.
```

The belief engine should use calibrated reliability:

```text
calibration(source, claim_type, context)
```

not raw model self-assessment.

## Calibration methods

The evaluation harness should track:

```text
predicted confidence
human verdict
test result
runtime confirmation
later contradiction
```

Then compute:

```text
calibration curves
Brier-style error
false positive rate
false negative rate
per-analyzer reliability
```

The goal:

```text
A claim with 0.80 confidence should be correct approximately 80% of the time
within its scope and claim class.
```

# 21. Belief Calculus Example

## Initial state

Requirement:

```text
REQ-014:
  Password reset tokens must expire after 15 minutes.
```

ADR:

```text
ADR-008:
  Use signed tokens with max_age 900 seconds.
```

Code:

```elixir
Phoenix.Token.verify(MyAppWeb.Endpoint, @salt, token, max_age: 900)
```

Test:

```elixir
test "expired token is rejected after 15 minutes"
```

Belief state:

```json
{
  "claim": "Password reset tokens expire after 15 minutes.",
  "claim_type": "architecture_commitment_realized_by_code",
  "state": "verified",
  "support_score": 0.94,
  "refute_score": 0.03,
  "evidence": [
    "accepted requirement",
    "accepted ADR",
    "current code span",
    "passing test"
  ]
}
```

## PR changes code

New code:

```elixir
Phoenix.Token.verify(MyAppWeb.Endpoint, @salt, token, max_age: 3600)
```

Belief revision:

```json
{
  "claim": "Password reset tokens expire after 15 minutes.",
  "state": "drifted",
  "support_score": 0.81,
  "refute_score": 0.76,
  "contradiction_type": "doc_code_drift",
  "intent_state": "accepted",
  "implementation_state": "refuted",
  "recommended_action": "restore_code_or_update_architecture"
}
```

PR output:

```text
Architecture drift detected.

The accepted security requirement and ADR still specify 15-minute reset token expiry.
This PR changes the implementation to 60 minutes.

Required resolution:
  1. restore max_age: 900, or
  2. update REQ-014, ADR-008, tests, and user/support documentation.

CI recommendation:
  block unless this change includes an explicit architecture decision update
  or approved policy exception.
```

That is the behavior the system should have.

# 22. Belief Calculus as Product Differentiator

A normal code graph can say:

```text
This function calls Phoenix.Token.verify/4.
```

A semantic code tool can say:

```text
This function verifies a password reset token.
```

The belief-calculus system can say:

```text
This function used to implement the accepted 15-minute reset-token commitment.
The current PR changes it to 60 minutes.
That contradicts the security requirement and ADR.
The existing test is stale or failing.
This is architecture drift, not merely a code change.
The PR should either restore the previous value or update the upstream decision record.
```

That is a qualitatively different product.

# 23. Minimal Implementation Plan

This does not require solving every reasoning problem at once.

The first usable version can implement a constrained belief engine.

## Phase 1: Claim normalization

Convert generated facts into structured claims:

```text
subject
predicate
object
qualifiers
scope
claim_type
source
```

Example:

```json
{
  "subject": "Accounts.Token.verify_reset_token/1",
  "predicate": "uses_token_max_age",
  "object": "900_seconds",
  "claim_type": "implementation_behavior",
  "scope": {
    "snapshot": "main@abc123"
  }
}
```

## Phase 2: Evidence attachment

Attach evidence to claims:

```text
source span
test span
requirement span
ADR span
runtime observation
human annotation
static analyzer output
LLM inference
```

## Phase 3: Evidence weighting

Implement the contextual authority matrix.

Do not overfit early. Start with explicit weights by claim type.

## Phase 4: State classification

Implement states:

```text
believed
verified
stale
contested
refuted
drifted
unimplemented
unverified
```

These eight states are enough for a strong first product.

## Phase 5: Invalidation

Tie claims to dependency hashes:

```text
source hash
AST hash
doc hash
test hash
policy hash
runtime window
```

If dependency changes, mark claims stale and recompute locally.

## Phase 6: PR review integration

The first killer workflow:

```text
PR opens
changed artifacts identified
affected claims recomputed
drift/violation/unverified states surfaced
exact evidence shown
required resolution suggested
```

This makes the belief calculus immediately valuable.

# 24. Required Engine Components

The belief calculus should be implemented as a set of services or modules:

```text
Claim Compiler
  Converts facts, docs, code analysis, and LLM output into structured claims.

Evidence Extractor
  Produces support/refute evidence from code, tests, docs, runtime, and users.

Evidence Weighter
  Applies authority, freshness, specificity, directness, independence, calibration.

Belief Evaluator
  Computes support/refute scores and belief state.

Contradiction Classifier
  Labels doc/code drift, test/code mismatch, runtime/design mismatch, etc.

Invalidation Engine
  Tracks source dependencies and marks stale claims after changes.

Propagation Engine
  Pushes belief changes across requirement → decision → contract → code → test → runtime paths.

Explanation Renderer
  Produces human-readable “why the system believes this” output.

Calibration Engine
  Updates reliability of analyzers and models from human feedback and later outcomes.
```

These are the operating intelligence components that sit above the representational substrate.

---

# 25. Design Principle

The belief engine should avoid pretending it has one universal truth.

Instead, it should maintain:

```text
truth by scope
truth by evidence class
truth by time
truth by authority
truth by current best model
```

So the system can say:

```text
Architecturally intended: X.
Currently implemented: Y.
Tested behavior: Z.
Observed production behavior: W.
Human-approved exception: E.
Current state: drifted but exceptioned in prod only.
```

That kind of nuanced truth maintenance is the difference between a useful architecture intelligence system and an overconfident graph browser.
