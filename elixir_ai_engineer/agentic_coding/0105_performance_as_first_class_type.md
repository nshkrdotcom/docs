The core is **compositional denotational semantics with performance as a first-class type**.

Here's what that means precisely. Every piece of software has two representations — what it *does* and what it *costs*. Current formal methods handle the first (types, contracts, state machines) and treat the second as a measurement concern. That split is the fundamental error. Performance isn't a property you measure after the fact — it's a *semantic dimension* of the program, meaning it should be encoded in the model of what the program *is*, not appended as a test after.

The theoretical foundation already exists in pieces. **Refinement types** (Liquid Haskell, F*) let types carry proofs — a function's type can assert "returns sorted list" not just "returns list." **Quantitative type theory** (Atkey, McBride) extends this to resource consumption — types that track how many times a resource is used, how much time or memory a computation costs. **Effect systems** compose these — if performance is an effect, it propagates through the type system compositionally. A change that violates a performance contract is a *type error*, not a test failure. The Codex bind group slot 30 mistake would have been a type error — it changed the resource profile of the binding architecture in a way that violated the type of the function.

The reason this is bounded — your complexity concern — is exactly compositional semantics. If each component has a bounded semantic description and your composition operators are finite and well-defined, the whole system's semantic model is bounded by the composition, not by the state space. You never enumerate states. You reason about *transformations between semantic domains*. This is the morphism. A valid change is a morphism in your semantic category — it preserves the structure of the denotation. An invalid change is not a morphism. That's the full formalization of "the agent needs to know this is bad."

**The naming problem dissolves here.** In a properly typed semantic model, names are handles into a semantic space — the name carries its semantic content because the type *is* the specification. This is why dependent type systems effectively solve naming: `commit_hlc_monotonic_append` isn't a naming convention, it's a proof-carrying term. The LLM doesn't need to respect naming conventions — it needs to inhabit a type system where the name and the contract are the same thing.

**The engineering core:** you need a domain-specific type system for your platform — not Dialyzer's success typing, which is after-the-fact — but a *specification-first* type system where architectural contracts including performance bounds are encoded as types, composition is bounded, and tests are derived mechanically from the type signatures. The LLM's job is translating architecture documents into that type system. Once it's in the type system, everything else — tests, invariant checks, coverage — is derivation, not authorship. The agent can't violate an invariant for the same reason a function can't return the wrong type: the model of the program doesn't permit it.

That's the machine you're at the center of.
